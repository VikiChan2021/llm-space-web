# LLM Space Web 后续优化方案与免费模型切换

调研日期：2026-10-04。本文区分当前源码、本次真实运行、线上发布与尚未验证的商业假设。产品优化部分为建议；本次已获授权实施的范围是免费模型切换及必要的恢复文案、使用说明与验证。

## 核心判断

建议继续把 LLM Space Web 打磨为「能解释、调试并验证改进的 Agent 工作台」，面向已经会一点编程、正在学习做 AI 应用的人。下一轮先完成用户的迭代闭环：运行 → 看模型和工具过程 → 修改一个因素 → 再运行 → 比较 → 留下验证记录。

你已有前端经验，这条路线能展示流式交互、工具执行、安全边界、状态恢复、实验设计和产品判断，适合 AI 应用工程与 Agent 前端岗位。当前项目没有真实用户，推广渠道也有限，先把它做成可验收、可演示的求职作品，同时寻找小规模外部使用证据。现在无法据此判断商业成功概率或估算收入。

现状的主要问题是可用性、可发现性和证据不足。工作台同时呈现 Models、Tools、Variables、提示词、消息、历史和助手；初学者可能不知道当前任务和下一步。中英文操作名混用也增加理解成本。继续增加平台能力之前，应先确认一个新用户可以完成一轮有理由的改进。

## 免费模型选择及边界

本次真实 API 探测结果（只记录脱敏结果）：

| 入口 | 结果 | 用法 |
| --- | --- | --- |
| 硅基流动 Qwen/Qwen3-8B | 文本请求 200，强制 weather_report 工具调用 200；项目本地完整天气闭环成功 | 默认；固定模型便于学习和比较 |
| OpenRouter openrouter/free | 文本请求 200，响应实际路由到免费 Nemotron；工具调用 200，返回 usage.cost=0 | 手动备用；实际模型可能变化，不宜作为固定评测基线 |
| OpenRouter qwen/qwen3.8-27b:free | 文本请求 200，usage.cost=0；该次短请求约 26.6 秒 | 固定模型备用；这不是稳定延迟统计，也不能据单次请求声称比默认模型更好 |

硅基流动官方当前价格页把 Qwen3-8B 列为零单价并支持函数调用。OpenRouter 的免费路由根据请求需要选择免费模型；免费请求仍受账号限制。本次首次读取 OpenRouter 账号状态时，免费档每日限制为 50、已用为 0；后续测试已经消耗部分次数，不能把 50 写成当前剩余额度。硅基流动旧 user/info 接口返回 410，不能据此推断 Key 无效或余额为零。

来源：[硅基流动价格](https://www.siliconflow.cn/pricing)、[硅基流动官方接入说明](https://docs.siliconflow.cn/docs/usercases/use-siliconcloud-in-translate-js)、[OpenRouter 免费路由](https://openrouter.ai/openrouter/free)、[OpenRouter 额度与错误](https://openrouter.ai/docs/api_reference/limits)。访问于 2026-10-04。

本站的「20 次/浏览器/天」与供应商账号额度是两层限制。一次完整 Agent 任务可能消耗两次或更多模型请求；例如 10 个案例 × 2 个变体 × 2 个模型回合约需 40 次请求，还未包含重试。不要把公共免费额度当成可持续 SaaS 的成本方案。

本次保持手动切换，不自动转到付费模型，也不在后台偷偷换实验对象。旧 Thread 的模型和历史不静默改写；若旧 Thread 仍选择 GLM，需从 Models 手动选新模型。服务器仅允许配置好的供应商和模型白名单，拒绝客户端伪造付费模型或供应商。Key 只放服务器配置和 Git 忽略的本地环境文件。

## 下一轮主方案：首次可解释改进 V1

目标用户：会基础前端或脚本，已能调用模型，但不会判断一次提示词或工具配置修改是否有效的人。

用户应看到一条短路径：

1. 选择一个具体任务，默认准备模型、工具、提示词与输入；清楚标注是否调用真实模型及预计额度。
2. 完成一次运行后，突出「查看过程」：实际模型、工具参数、工具结果、最终答案、耗时和调用次数。
3. 给一个明确改进目标，例如天气回答必须包含来源与查询时间；一次只改变提示词，保持模型和案例一致。
4. 再次运行后自动准备前后两次结果的比较，说明这次改变了什么，展示证据，再允许人工评价。
5. 保存简短改进记录；刷新后能继续。评测入口从 More actions 提升为容易找到的「质量验证」，直接复用现有实验与数据模型。

先把天气案例做好，但不要把实时天气当稳定质量测试集。正式比较应使用固定输入和可重放的工具结果，另设一次在线天气演示。扩展只做 3 个明确任务：带来源的查询、约束明确的摘要、固定资料的结构化提取。每个任务都有预期规则和故意失败的输入，避免模型恰好说得好就宣称改进有效。

本次 OpenRouter 完整运行中，模型先搜索了错误年份的天气，随后才调用天气工具并用 2026-10-04 的工具结果纠正答案。这说明后续需把 current_date 明确写入上下文、检查日期与来源，并减少不必要的搜索。默认 Qwen3-8B 的这次回答也没有显式列出来源；「可运行」与「符合质量规则」必须分开验收。

免额度示例可以解释界面，但必须显著标注「预置演示结果」，并与真实模型实验分开；它不能替代真实 Run 证据。已有 Pilot Bundle 可用于此路径，不应再建一套导入与保存系统。

### 一个核心指标

新用户在无现场指导时，10 分钟内完成一次「首轮运行 → 检查工具过程 → 修改 → 第二轮运行 → 比较并说明理由」的比例。

- 基线：尚无外部测试，未测。没有真实用户不能写成实测 0% 转化率；本次模型冒烟成功也不是产品激活证据。
- V1 目标：首批 5 位目标用户中至少 4 位完成，且可以说明变更因素和一个剩余风险。小样本只用于发现阻碍，不用于估计全体用户表现。
- 测量：观察 5 次使用，记录完成步骤、耗时、卡点；内容无关事件只发状态、步骤枚举、数量、耗时，不发 Prompt、答案、图片、文件、Key 或工具结果。
- 护栏：首轮失败可恢复；刷新不丢数据；已有 Thread 不覆盖；停止不是成功；供应商的 SSE 中途错误不是成功；比较时模型变更有明确提示。

### 时间与依赖

建议再投入约 60 小时，按每周 10 小时分成 6 周。这是投入上限建议，不是开发工时承诺。

| 阶段 | 预算 | 交付与验收 |
| --- | --- | --- |
| 1：稳定与恢复 | 8 小时 | 固定模型基线、错误与额度说明、旧 Thread 恢复、首次成功冒烟；本次已解决大部分模型接入问题 |
| 2：首次改进路径 | 17 小时 | 逐步引导、中文主要操作、可发现的历史与质量入口；新用户能完整操作 |
| 3：可重复的证据 | 15 小时 | 三个有固定输入和判定规则的任务、前后比较、现有评测 V2 的独立验收与发布；不把单次改进说成整体提升 |
| 4：加载与展示 | 8 小时 | 测首屏请求和可交互时间，按实际瓶颈延后评测/编辑器/助手资源；准备架构图和 3 分钟演示 |
| 5：外部验证与复盘 | 12 小时 | 找 5 位 AI 应用学习者或前端开发者试用，修复主要阻碍，整理面试案例和下一步决定 |

预算可随外部反馈调整。先用 2 个真实完整任务测量，再决定是否有必要进一步拆包；构建的体积警告不能替代性能测量。

可能涉及：apps/web/src/guest/guest-workbench.tsx、guest-first-success.ts 与 callout、coach/weather-learning-*、guest-evaluation-lab-dialog.tsx、guest-evaluation-analytics.ts；共享的运行历史/比较/实验语义分别在 packages/ui 与 packages/core。文案、引导和状态联动优先放 Web 层，核心实验语义保持共享。部署前核对线上与本地版本，不把未验收的 V2 捎带发布。

验证需要覆盖：新浏览器首次成功、第二次改进与比较、旧数据保留、刷新恢复、主动停止、供应商流式失败、浏览器额度耗尽和不可用模型。可见界面分别在桌面与 390px 验证布局、键盘、焦点和溢出；配套运行相关 Bun 测试、mise run check:changed、mise run build:guest-web、mise run pack:guest-api 和 git diff --check。关键失败、数据损坏或不可解释的付费回退应阻止发布。

## 两个备选方向

**备选一：纯中文 AI 学习产品。** 与你的前端和学习内容兴趣吻合，也更容易找个人试用。但需要内容质量、习惯形成与获客，免费课程和通用助手替代性强。可作为案例与推广入口；暂不另外做完整课程平台或英语学习产品。

**备选二：企业 Agent 评测与协作 SaaS。** 可复用已有评测、Review Queue 和 Pilot Bundle，客单价假设更高。但目前没有渠道、真实场景或付费客户，同时涉及账户、租户、权限、数据保护、部署和持续支持。只有找到能提供真实测试集并愿意参与试点的团队，才值得进入这个方向。

## 求职和商业验证如何共用这次投入

面试演示建议围绕一个可复现问题讲：初始 Agent 漏来源 → Trace 判断是提示词约束问题 → 保持模型固定修改提示词 → 用规则和人工复核验证 → 展示没有改善或发生回归的情况。补上本次供应商额度故障、白名单校验、SSE 错误脱敏和旧数据保护，可以形成可信的工程案例。不要把上游框架已有能力当成个人原创，要说明你复用了什么、解决了什么、如何验证。

商业方面，先招募 5 位试用者，不做大规模投流。可以在允许展示项目的开发社区发布短案例和可运行链接，也可请前同事实际操作。重点问他们上一次如何调试 Agent、哪里耗时、现有工具哪里不合适，并观察是否主动回来完成第二个任务。喜欢演示、愿意留邮箱都弱于重复使用。

若有人有同类实际任务，可以提出一项小范围人工协助的调试/验证服务，再检验是否愿意付费；价格需通过具体报价测试，本文不推定支付意愿。连续两周无法接触到测试者，应暂停继续堆功能，把时间转向作品演示和求职。若能接触人但 5 人中多数不能完成第一轮任务，先修主路径；若能完成却无人再次使用，再调整价值主张。尚无真实使用前，不先投入登录、支付、团队协作、复杂多 Agent、长期记忆或大范围模型目录。
